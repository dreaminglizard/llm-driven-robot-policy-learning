# intent_sketch.v1 대조의 사전 평가 규칙

이 문서와 코드·보충 자료는 실제 생성 전에 고정한다. 원본 `independent_ko_en_20261030_v2/development80.jsonl`의 발화·문맥·`expected_any_of`·`grading_reason`은 수정하지 않는다. 원본 자료는 이미 분석에 사용한 개발 자료이며 두 경로 모두 같은 80건을 분모로 사용한다. 이 작업에서 모델 호출이나 실행은 없다.

## 두 출력과 변환

- A는 기존 상세 프롬프트와 `task_program.v2` 전체 제안이다. 원시 JSON과 기존 v2 검사기 수용 결과를 기존 `judge.projection`과 비교한다.
- B는 발화만 받은 모델의 `intent_sketch.v1`이다. 추가 기록을 임의 생성하지 않고 구조·실제 발화 근거를 확인한 뒤, 동일 접수 문맥에서 참조를 결속한다. 원시 스케치, 결속 근거·요구되는 재검사, 범위 판정, v2 변환 가능성, 기존 v2 검사기 결과를 각기 보존한다. 이 계층은 읽기 전용 모의 제안이며 어떤 작업도 실행하지 않는다.
- 긍정 요청은 최대 8개, 제외·질문·미확정은 별도로 최대 8개, 전체 의미 기록은 최대 16개다. `prior_steps`의 원래 인덱스는 제외 기록을 포함한 전체 배열의 위치다. v2 변환에서는 제외 기록을 실행 단계로 넣지 않고 인덱스를 명시적으로 다시 매핑한다. 기존 v2 자체의 총 8기록 한도를 초과하거나 필수 항목이 빠지면 전체 스케치를 보존하고 변환 불가로 기록한다. 한도를 넘는 결과를 잘라 성공 처리하지 않는다.
- B에서 `query`는 비실행 질문, `exclude`만 있으면 해당 작업의 부정으로 간주한다. 비실행의 공통 결과를 원본 `clarify.question_only` 또는 `clarify.negated_only`와 대응시킬 수 있지만, 실제로 질문에 답하거나 정지 행동을 새로 생성한 것으로 보지 않는다. 불명확한 쌓기의 미지정 출발지처럼 모델이 명시한 목표를 보존하고 빠진 필드만 판정했을 때는 원본의 `clarify.missing_target` 또는 `clarify.ambiguous_reference`와 비실행 결과를 비교한다.
- B가 범위 밖 숫자를 보존해 지원 범위 검사에서 차단되면 원본의 `clarify.unsupported`와 **비실행 결과**를 비교한다. v2 검사기는 이 범위 밖 작업을 표현할 수 없으므로 `not_representable`로 기록하며 검사 통과로 세지 않는다. B가 범위 밖 원래 요구 대신 막연한 `clarify.unsupported`만 내면 비실행 결과는 같을 수 있어도, 아래의 원래 요청 보존 점수는 실패다.
- 주 대조의 수치 인자는 정수이며 숫자 문자열 후보는 사용하지 않는다. 오프라인 b11960 변환 문법은 정수에 최대 16자리를 허용한다. 더 긴 수는 숫자를 줄여 넣지 않고 원래 숫자가 포함된 발화 근거와 `clarify.unsupported`의 미확정으로 나타내도록 프롬프트에 명시했다. 이 규칙이 실제 모델에서 지켜질지는 아직 측정하지 않았다. 현 80건의 범위 밖 값은 3과 5다.
- v2로 충실하게 변환된 B 제안만 A와 같은 변경 없는 v2 검사기에 적용한다. 빠진 수량을 1로 채우거나 빠진 대상을 상태에서 추측하지 않는다. 구조상 필요한 v2 `null`은 미지정을 뜻할 뿐 실제 수량·대상을 부여하지 않는다. 파싱 오류·스키마 오류·근거 오류·미완료·시간 초과는 분모에 남는다.

## 원래 요청과 범위의 별도 보존 기준

기존 정답은 그대로 사용한다. 원래 정답의 `clarify`만으로는 범위 밖 숫자나 빠진 대상이 무엇이었는지 구조적으로 비교할 수 없어, **원문에서 확인한 별도 속성**을 다음 자료에 둔다. 이 자료는 정답 프로그램 변경이 아니다. 작성자는 이전 결과를 본 Codex AI이므로 독립적인 눈가림 라벨이라고 주장하지 않는다. 모델 요청에는 원본 정답, 보충 속성, 판정 이유를 보내지 않는다.

- `unsupported_extraction_expectations.jsonl`: 6건의 요청 동작과 명시된 자리·원통·층을 확인한다. 세 층 쌓기는 원래 출발·도착·높이를 담은 한 쌓기 목표 또는 원문 순서를 보존한 이동 뒤 쌓기로 표현할 수 있다. 높이만 맞고 다른 대상을 만들어 내면 일치하지 않는다.
- `missing_target_extraction_expectations.jsonl`: 출발을 모르는 쌓기 2건에서 쌓기 목적지 3번을 보존했는지 확인한다. 원통 ID·출발지를 임의로 더하면 일치하지 않는다.
- `scope_evidence_expectations.jsonl`: 명시된 부정·정정 16건의 제외 동작이나 제외된 값과 그 대상·부정 표현이 실제 근거 구절에 있는지 확인한다. 이전 작업 반복의 제외와 현재 반복 종료를 바꿔 세지 않는다. 반복 대상의 제외는 별도 `exclude` 단계 또는 해당 긍정 반복의 `reference` 제외로 표현할 수 있다. 이 고정 사례의 대소문자 무시 문자열 포함 검사만으로 일반 언어의 의미를 보증하지 않는다. 이전 표지는 보존하되 이 보완 표지를 채점에 사용한다.

세 자료에 없는 원본 정답 대안은 기존 의미 투영으로 그대로 비교한다. 위 보충 속성이 있는 경우 B는 그 속성도 보존해야 **엄격한 보존 정답**이다. A의 기존 형식이 해당 속성을 구조적으로 나타내지 못하면서 원본 비실행 의미는 맞춘 경우는 오답이나 보존 성공으로 단정하지 않고 `not_representable`로 센다. 형식 오류나 이미 틀린 제안은 `not_representable` 뒤에 숨기지 않고 실패다. 전체 80건을 유지하고 성공·실패·표현 불가·질문 미확정을 별도로 보이며, 필요하면 가능한 점수 범위만 제시한다.

## 수동 검토와 보고

원시 `clarify`는 정답 여부와 무관하게 모두 목록화한다. 검토자는 문구·발화·문맥·기준을 읽고 식별자, 주체, 이유와 `appropriate`·`inappropriate`·`absent`·`uncertain`, 의미 일치 여부를 기록한다. 키워드 존재만으로 정답을 정하지 않는다. 이미 형식이나 내용이 틀린 경우에는 수동 검토가 대기 중이어도 그 실패를 분모에서 빼지 않는다. 질문이 `null`이거나 생략되면 실제 질문 없음으로 기록한다. 사용자 질문을 행동으로 바꾸지 않은 것과 답변한 것은 별개다.

두 경로 각각 전체·언어별·기능별로 형식 성공, B의 원시 작업 순서와 보존 속성, 문맥 결속 후 의미, v2 검사 후 의미, 잘못 수용된 해결 행동 포함 제안, 과도한 차단·정지 누락, 확인 질문을 나눈다. A와 B의 짝별 개선·퇴행과 시간·입출력 토큰도 남기며, 한 번씩 생성한 개발 자료의 결과를 안정성 일반화나 독립 최종 시험으로 부르지 않는다. 다른 서버 부하·캐시가 같다는 근거가 없으면 지연을 속도 개선 증거로 쓰지 않는다.
